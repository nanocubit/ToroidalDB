# Оптимизация TQL запросов

## Введение

Этот документ содержит рекомендации по оптимизации производительности TQL v2.0 запросов в ToroidalDB. Следование этим рекомендациям поможет улучшить время отклика и уменьшить нагрузку на систему.

## 1. Общие принципы оптимизации

### 1.1. Использование LIMIT

Всегда используйте LIMIT в своих запросах, особенно при разработке:

```
-- Хорошо
MATCH (doc:Document) WHERE TOROIDALDISTANCE(doc.vector, 0.3) RETURN doc.id LIMIT 10

-- Плохо (может вернуть много результатов)
MATCH (doc:Document) WHERE TOROIDALDISTANCE(doc.vector, 0.3) RETURN doc.id
```

### 1.2. Оптимальные пороги расстояния

Выбирайте оптимальные значения порога для TOROIDALDISTANCE:

- Маленький порог (0.1-0.2) - быстрее, но меньше результатов
- Большой порог (0.4-0.5) - медленнее, но больше результатов
- Рекомендуемый диапазон: 0.2-0.3 для большинства случаев

### 1.3. Фильтрация на ранних этапах

Применяйте фильтры как можно раньше в запросе:

```
-- Оптимально: фильтрация до вычисления расстояния
MATCH (user:User {active: true}) WHERE TOROIDALDISTANCE(user.profile_vector, 0.25) RETURN user.id LIMIT 5

-- Менее эффективно: сначала вычисляем расстояние, потом фильтруем
MATCH (user:User) WHERE TOROIDALDISTANCE(user.profile_vector, 0.25) AND user.active = true RETURN user.id LIMIT 5
```

## 2. Оптимизация графовых запросов

### 2.1. Ограничение глубины обхода

При использовании графовых обходов ограничивайте глубину:

```
-- Хорошо: ограничение 3 шагами
MATCH (doc:Document) CONNECTEDTO(doc, "TAGGED_WITH", "tech") WITHIN 3 HOPS RETURN doc.id LIMIT 20

-- Опасно: без ограничения может привести к очень долгому выполнению
MATCH (doc:Document) CONNECTEDTO(doc, "TAGGED_WITH", "tech") RETURN doc.id LIMIT 20
```

### 2.2. Использование индексов

Храните часто используемые свойства в индексах. В TQL это неявно, но учитывайте:

- Свойства в MATCH клаузах эффективнее для фильтрации
- Используйте конкретные значения вместо шаблонов, где это возможно

## 3. Агрегации и производительность

### 3.1. Оптимизация агрегационных запросов

Для агрегаций используйте фильтрацию до вычисления агрегатов:

```
-- Эффективно: фильтрация до агрегации
MATCH (user:User {country: "US"})-[:LIKES]->(content:Content) 
RETURN user.id, COUNT(content) AS likes 
ORDER BY likes DESC 
LIMIT 10

-- Менее эффективно: сначала соединяем, потом фильтруем
MATCH (user:User)-[:LIKES]->(content:Content) 
WHERE user.country = "US" 
RETURN user.id, COUNT(content) AS likes 
ORDER BY likes DESC 
LIMIT 10
```

### 3.2. Избегайте сложных вложенных агрегаций

Сложные вложенные агрегации могут замедлить выполнение запроса. Рассмотрите разбиение на несколько запросов:

```
-- Лучше избегать таких конструкций
MATCH (user:User)-[:CREATED]->(post:Post)-[:HAS_TAG]->(tag:Tag) 
RETURN user.id, COUNT(post), AVG(size(collect(tag.name))) AS avg_tags_per_post
```

## 4. Распределенные запросы

### 4.1. Когда использовать DISTRIBUTED

Используйте ключевое слово DISTRIBUTED для:

- Запросов, охватывающих большие объемы данных
- Запросов, требующих высокой доступности
- Запросов, где важна отказоустойчивость

```
-- Хороший кандидат для распределенного выполнения
DISTRIBUTED MATCH (item:Item) WHERE TOROIDALDISTANCE(item.embedding, 0.2) RETURN item.id, item.score LIMIT 100
```

### 4.2. Оптимизация распределенных запросов

- Минимизируйте количество данных, передаваемых между шардами
- Используйте локальные фильтры перед глобальной агрегацией
- Учитывайте топологию шардирования при проектировании запросов

## 5. Кэширование и повторяющиеся запросы

### 5.1. Идемпотентные запросы

Для часто повторяющихся запросов с одинаковыми параметрами система использует кэширование:

```
-- Эти запросы будут кэшироваться отдельно
MATCH (doc:Document) WHERE TOROIDALDISTANCE(doc.vector, 0.2) RETURN doc.id LIMIT 5
MATCH (doc:Document) WHERE TOROIDALDISTANCE(doc.vector, 0.25) RETURN doc.id LIMIT 5
```

### 5.2. Параметризованные запросы

Хотя TQL v2.0 не поддерживает параметры напрямую, структурируйте свои запросы для эффективного кэширования:

- Используйте одинаковые шаблоны запросов
- Изменяйте только значения, а не структуру запроса

## 6. Мониторинг и профилирование

### 6.1. Использование метрик

Следите за следующими метриками:

- Время выполнения запроса
- Количество затронутых узлов
- Использование памяти
- Загрузка CPU

### 6.2. Идентификация медленных запросов

Для идентификации медленных запросов:

- Используйте логирование запросов
- Мониторьте 95-й и 99-й перцентили времени выполнения
- Анализируйте запросы с высокой частотой выполнения

## 7. Практические примеры оптимизации

### Пример 1: Оптимизация поиска похожих элементов

```
-- До оптимизации
MATCH (item:Item) WHERE TOROIDALDISTANCE(item.features, 0.4) RETURN item.id, item.name ORDER BY item.score DESC LIMIT 50

-- После оптимизации
MATCH (item:Item {category: "electronics"}) 
WHERE TOROIDALDISTANCE(item.features, 0.25) 
RETURN item.id, item.name, item.score 
ORDER BY item.score DESC 
LIMIT 20
```

### Пример 2: Оптимизация графового анализа

```
-- До оптимизации
MATCH (user:User)-[:FRIEND_OF*1..5]->(friend:User) WHERE friend.location = "New York" RETURN user.id, count(friend)

-- После оптимизации
MATCH (user:User)-[:FRIEND_OF*1..2]->(friend:User) 
WHERE friend.location = "New York" 
RETURN user.id, count(friend) 
LIMIT 100
```

## 8. Инструменты профилирования

### 8.1. Встроенные средства

- Используйте `/metrics` endpoint для получения Prometheus метрик
- Проверяйте логи на наличие медленных запросов
- Используйте админку для мониторинга производительности

### 8.2. Внешние инструменты

- Интеграция с системами APM (Application Performance Monitoring)
- Использование систем логирования (ELK stack, etc.)

## 9. Лучшие практики

1. **Тестируйте на реальных данных** - производительность может отличаться на тестовых и реальных наборах данных
2. **Используйте инкрементное усложнение** - начинайте с простых запросов и постепенно добавляйте сложность
3. **Мониторьте использование ресурсов** - следите за потреблением CPU, памяти и дискового пространства
4. **Регулярно обновляйте статистику** - актуальная информация о данных помогает оптимизатору принимать лучшие решения
5. **Документируйте оптимизированные запросы** - создайте внутреннюю документацию с примерами эффективных запросов

## 10. Заключение

Оптимизация TQL запросов - это итеративный процесс. Регулярно анализируйте производительность ваших запросов и применяйте описанные техники для достижения наилучших результатов.
